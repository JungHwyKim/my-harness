# code-tracker

**이 스킬이 만드는 것은 지적이 아니라 설명이다.** `rag-code-review` 는 *이 코드가 규칙을
어겼나* 에 답하고 독자가 이미 저장소를 안다고 전제한다. 여기는 *이 코드가 무슨 일을 하나* 에
답하고 **독자가 저장소를 모를 수 있다고 전제한다.**

## 이 스킬의 핵심은 설명이 아니라 출처다

설명은 그럴듯하게 쓰기 쉽다. 어려운 것은 **읽는 사람이 어느 문장을 믿을 수 있는지 아는
것**이다.

2026-09-03 세션에서 실제로 밟았다. 「코드만 읽고 기능을 목록으로」 요청에 목록을 냈는데,
그중 여섯 항목이 코드가 아니라 `CLAUDE.md` 지식에서 온 것이었다. 사용자가 짚어 코드로 확인해
보니 여섯 다 실재했지만 — **그때까지는 어느 문장이 관측이고 어느 문장이 전언인지 아무도
몰랐다.** 덤으로 코드를 직접 훑으니 문서에 없던 기능 열다섯이 더 나왔다(대각선 셀 분할,
텍스트 인코딩 자동 감지, Vision 응답 구제 파싱 등).

그래서 **모든 주장에 파일·심볼을 단다.** 못 단 문장은 「추정」으로 표시하거나 안 쓴다.
이것을 빼면 이 스킬은 그냥 그럴듯한 산문 생성기다.

## 1단계 — 범위를 확정한다

1. 인자가 경로면 그것 (`/code-tracker rag_pipeline/retrieval/`)
2. 인자가 없으면 `git diff HEAD` — 변경분을 대상으로 삼는다
3. 둘 다 비면 사용자에게 **한 번** 묻는다. 저장소 전체를 임의로 고르지 않는다

**범위를 스스로 넓히지 않는다.** 사용자가 폴더 하나를 줬는데 "관련이 있어 보여서" 옆 폴더를
끌어오면 산출물이 사용자가 시킨 것과 달라지고, 그것이 길이 상한을 밀어 올린다.

## 2단계 — 코드를 읽는다

**여기가 먼저다. 위키를 먼저 읽으면 그 문장이 코드를 읽은 결과처럼 산문에 섞인다.**

읽는 것은 셋이다.

- **모듈 docstring** — 이 저장소는 *왜* 를 여기 적는 컨벤션이라 3절의 주 재료다
- **공개 심볼** — `grep -nE '^(async )?def [a-z]|^class [A-Z]'` 로 훑고, 필요한 것만 본문을 연다
- **호출 관계** — 2절 다이어그램의 재료다. **`grep` 으로 실제 호출을 확인한 것만 실선이다**

**연 파일과 확인한 심볼을 그때그때 적어 둔다.** 4단계에서 각주와 「읽은 파일」 목록이 그것
하나에서 나오고, 나중에 되짚으려 하면 무엇을 실제로 봤는지 이미 흐려져 있다.

## 3단계 — 위키와 대조한다

`.claude/wiki/knowledge/README.md` 의 라우팅 표로 그 영역 문서를 찾아 읽는다. 표에 없는
영역이면 `.claude/wiki/knowledge/contracts.md` 만 본다.

우선순위는 `rag-code-review` 가 이미 쓰는 것과 같다.

```
실제 코드·테스트  >  knowledge/  >  CLAUDE.md  >  추측
```

**어긋난 자리를 고치지 않는다.** 문서도 코드도 안 고치고 **산출물 5절에 적는다.** 이 스킬은
읽기 전용이고, 반영은 별도 작업이다(`rag-code-review` 의 「reference 제안」과 같은 자리다).

**대조에서 얻은 문장은 각주를 위키 쪽으로 단다.** 코드에서 온 것과 섞으면 1단계에서 말한
바로 그 문제가 재현된다.

## 4단계 — 산출물을 만든다

`<이 스킬 폴더>/template.html` 을 뼈대로 쓴다. `<!-- CODE-TRACKER: ... -->`
주석이 각 자리에 무엇을 넣을지 적어 두었으니 **그 주석은 채우면서 지운다.**

낼 곳은 `output/code-tracker/` 다. 파일 이름은 범위에서 딴 슬러그이고, 같은 범위를 다시
돌리면 **덮어쓴다.**

> **`output/` 은 이미 `.gitignore` 에 있다.** 새로 추가하지 않는다. 커밋하지도 않는다 —
> 같은 이유로 `backend/preview.py` 의 산출물이 제외돼 있고 그 사유가 `.gitignore` 에
> *"템플릿을 고치면 곧바로 낡아 어느 시점의 화면인지 알 수 없게 된다"* 로 적혀 있다.
> 코드 설명은 정확히 같은 모양이다.

`--md` 를 받으면 같은 내용을 Markdown 으로 낸다. 두 층은 `<details>` 로, 각주는 괄호로 단다.
**둘을 동시에 내지 않는다** — 같은 사실이 두 파일에 생기면 한쪽만 다시 돌렸을 때 어긋난다.

### 절 구성 — 물음 순서

| 절 | 답하는 물음 | 층 |
|---|---|---|
| 1. 무엇을 하나 | 이 코드가 존재하는 이유. 3~5문장 | 바깥 |
| 2. 어떻게 도나 | 진입점 → 단계 → 나가는 곳 + 다이어그램 하나 | 바깥 |
| 3. 왜 이렇게 됐나 | 고른 것과 버린 것 | 안쪽 |
| 4. 조심할 것 | 되돌리면 조용히 깨지는 것 | 안쪽 |
| 5. 문서와 어긋난 자리 | 3단계의 결과 | 안쪽 |

**바깥 층에서는 내부 어휘를 쓰기 전에 표준 용어로 먼저 푼다.** `ParsedDocument` · RRF ·
「폴백 사슬」은 이 저장소 안에서만 통하는 말이다. 바깥 층의 독자는 그것을 모른다.

**3절은 근거가 있을 때만 쓴다.** docstring·주석에 *왜* 가 안 적혀 있으면 지어내지 말고
「이 범위의 코드에는 결정 근거가 남아 있지 않습니다」 한 줄로 닫는다.

**5절은 어긋난 게 없어도 "없음"을 적는다.** 절을 통째로 지우면 *대조를 안 했다* 와
*대조했는데 어긋난 게 없다* 가 안 갈린다.

### 다이어그램

`<pre class="mermaid">` 에 넣는다. 라이브러리를 못 받는 환경에서는 그 소스가 글자로 그대로
보이고 **그것이 폴백이다** — 따로 만들지 않는다.

- **실선(`-->`)은 코드에서 호출을 확인한 관계만.**
- 확인 못 한 관계는 **점선(`-.->`)이거나 아예 안 그린다.**

다이어그램은 글보다 강하게 각인되므로 틀리면 글보다 더 나쁘다. 확신이 없으면 안 그리는
쪽이 맞다.

### 근거 표기

주장 옆에 `파일.py:심볼()` 을 단다. HTML 은 위첨자 번호로 접히고 토글을 켜면 본문에 펼쳐진다
(템플릿이 CSS 만으로 처리하므로 손댈 것이 없다). Markdown 은 괄호로 단다.

- **파일만 적고 심볼을 빼지 않는다.** `pdf.py` 는 1,000줄이 넘어 되짚는 데 도움이 안 된다.
  `rag_pipeline/ingestion/loader/document/pdf.py` 처럼 긴 파일일수록 심볼이 곧 근거다
- **줄번호는 안 쓴다.** `CLAUDE.md` 가 *"한 줄만 밀려도 조용히 거짓이 되고 아무도 안
  알려준다"* 로 이미 그은 선이다
- 코드에서 확인 못 한 문장은 `<p class="guess">` 로 감싼다

### 머리말 수치도 주장이다 — 세지 않고 쓰지 않는다

**산출물 머리말의 「읽은 파일 N개 · 근거 N개」와 본문의 「엔드포인트 6개」 같은 수는 전부
관측이어야 한다.** 산문에는 근거를 달면서 수치는 눈대중으로 쓰기 쉬운데, 그것이 이 스킬이
막으려는 바로 그 종류다 — 틀린 수는 산문보다 더 확신 있게 읽힌다.

**두 회차 연속으로 밟았다.** 2026-09-04 `rag_pipeline/retrieval/` 에서 「근거 21개」라고
썼는데 실측 18개였고, 2026-09-05 `backend/app` 에서 「근거 24개」인데 실측 28개였다.
둘 다 브라우저 검증이 잡았고 **본문의 근거는 멀쩡한데 머리말만 틀렸다** — 즉 규율이
문장에만 걸려 있고 수치에는 안 걸려 있었다.

세는 방법은 산출물을 열어 재는 것이다.

```js
({ ev: document.querySelectorAll('.sources li[id]').length,
   files: document.querySelectorAll('footer ul li').length,
   dangling: [...document.querySelectorAll('.ev a')]
     .map(a => a.getAttribute('href').slice(1))
     .filter(id => !document.getElementById(id)).length })
```

**`dangling` 이 0이 아니면 어딘가의 각주가 목적지 없이 떠 있는 것이다.** 수를 맞추는 것보다
이쪽이 먼저다. Markdown 은 각주 목록과 본문 참조를 눈으로 대조한다.

**세기 전에는 머리말을 비워 두는 편이 낫다.** 임시로 채운 수는 고치는 것을 잊는다.

## 5단계 — 보고한다

터미널에는 짧게 낸다. 산출물을 그대로 대화에 옮겨 적지 않는다 — 그러면 파일을 만든 뜻이 없다.

- 만든 파일 경로
- 읽은 파일 수 · 단 근거 수
- **3단계에서 어긋난 자리가 나왔으면 그 수**. 0이면 0이라고 적는다

## 길이 — 한 파일에 안 들어갈 때

상한을 넘기면 **크기가 아니라 의미로 갈라** 파일을 나누고 목차 파일을 하나 둔다.
`.claude/wiki/knowledge/` 가 20,000자를 넘을 때 폴더로 승격하는 것과 같은 기준이다.

**넓은 범위를 한 파일에 우겨넣지 않는다.** 그러면 조용히 얕아지는데, 읽는 사람은 그것이
얕아진 설명인지 원래 그만큼인 코드인지 모른다.

## 이 스킬의 범위

**읽고 설명만 한다.** 코드도, 위키도, `CLAUDE.md` 도 고치지 않는다.

- 규칙 위반을 지적하는 것 → `rag-code-review`
- 실행 결과가 기대값과 맞는지 → `regression-test` · `document-ingestion`
- 아직 안 끝난 일을 모으는 것 → `openwork` (수집은 `openwork/collect.py` 가 한다)
- 무엇을 만들지 정하는 논의 → `plan-log`

설명하다 규칙 위반이 눈에 띄면 **5절에 한 줄 적고 넘어간다.** 지적을 시작하면 산출물이
두 가지 일을 하게 되고, 읽는 사람은 어느 쪽으로 읽어야 할지 모른다.

**`-m integration` 은 절대 돌리지 않는다.** 이 스킬은 코드를 읽을 뿐 실행하지 않는다.
