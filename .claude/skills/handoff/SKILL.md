# handoff

Codex는 설계·조사·결과 리뷰를 맡고 Claude Code는 구현·수정·테스트 실행을 맡는다. 두
에이전트가 같은 체크아웃을 보므로, 사용자는 내용을 복사하지 않고 경로만 넘긴다.

**인수인계는 사용자가 건다.** 파일을 쓰는 것이 다음 세션을 시작하지 않는다. 이 절차는
세션을 자동으로 잇는 장치를 두지 않는다. 다만 이미 승인된 단계 안의 작업은 다시 묻지 않고
잇는다.

넘길 때마다 체크아웃과 현재 리비전을 확인한다. 다른 worktree는 커밋되지 않은 파일을
공유하지 않는다. 같은 파일을 두 에이전트가 동시에 고치지 않는다.

## 파일과 소유

| 파일 | 소유 | 언어 | 수명 |
|---|---|---|---|
| `tasks/<작업 ID>.md` | Codex | 한국어 | 임시. 완료와 보존 뒤 Claude가 정리한다 |
| `tasks/<작업 ID>.review.md` | Claude | 영어 | 임시. 명세와 같은 정리 조건을 따른다 |
| `tasks/_template.md` | Codex. 명세를 쓰는 쪽이 영구 템플릿을 유지한다 | 한국어 | 남긴다 |
| `.claude/skills/handoff/SKILL.md` | 이 절차의 원본 | 한국어 | 남긴다 |
| `.claude/wiki/knowledge/<주제>.md` | 구현한 쪽 | 한국어 | 남긴다. 현재 계약과 동작 |
| `.claude/wiki/history/plan/` | Claude. 기존 `plan-log` 절차를 쓴다 | 한국어 | 결정 이유가 값을 할 때만 남긴다 |

**한 명세에 소유자는 하나다.** Claude는 검토 결과와 수정 제안을 리뷰 파일에 쓰고, 명세는
Codex가 제자리에서 고친다 — 그 작업 자체의 수정 요청일 때만이고, 새 작업은 아래 「작업
ID와 명세 파일」을 따른다. `doctor-revised.md`처럼 경쟁하는 명세를 만들지 않는다. 정리
책임이 명세를 고쳐 쓸 권한을 주지는 않는다. Git은 커밋된 내용만 보존한다 — 추적되지 않는
파일에는 되돌릴 이력이 없다.

## 작업 ID와 명세 파일

작업마다 고유한 작업 ID를 정하고 그 ID로 명세 파일을 새로 만든다. 한 파일에 서로 다른
작업을 계속 덧붙이면 Claude가 구현을 시작한 뒤에 기준이 달라진다.

- 작업 ID는 목적과 대상이 드러나는 영문 소문자와 하이픈으로 쓴다 — `quality-env-setup`,
  `template-history-cleanup`.
- 경로는 명세가 `tasks/<작업 ID>.md`, 리뷰와 구현 보고가 `tasks/<작업 ID>.review.md`다.
  두 파일은 같은 ID를 쓴다.
- `handoff.md`·`plan.md`·`task.md` 같은 범용 이름을 새 작업의 공용 명세로 다시 쓰지
  않는다. 날짜나 `v2`만으로 작업을 가르지 않는다.
- 쓰기 전에 같은 경로가 있는지 본다. 다른 작업이 이미 그 이름을 쓰고 있으면 대상과 변경
  목적을 더 붙여 가른다. 끝나서 지운 작업의 ID도 다시 쓰지 않는다 —
  `git log --all -- tasks/<작업 ID>.md`로 지난 이력을 본다.
- 초안은 Codex가 같은 파일에서 다듬어도 된다. 다만 Claude가 검토하거나 구현하는 중인
  명세는 본문과 경로를 그대로 둔다. 그 단계가 끝나고 그 파일을 읽는 에이전트가 없는 것을
  확인한 뒤에 고친다. 제자리 수정은 그 작업 자체의 수정 요청에만 쓰고, 다른 작업을 기존
  명세에 얹는 수단으로 쓰지 않는다.
- 새 작업, 범위 추가, 요구 변경은 핵심 내용을 담은 새 ID의 후속 명세로 만든다. 기존 명세를
  베낀 경쟁 문서가 아니라 바뀐 내용과 선행 관계가 분명한 다음 작업이어야 한다. 후속 명세를
  만들었다고 진행 중인 작업의 기준이 바뀌지는 않는다.
- 후속 명세에는 선행 작업과 그 관계를 적는다. 같은 구현 파일을 바꾸는 후속 작업은 선행
  작업이 끝난 뒤에 한다 — 파일 이름을 갈랐다고 구현 충돌이 사라지지 않는다.
- 명세의 상태 표기가 Claude에게 명세를 고칠 권한을 주지는 않는다. Claude가 본 상태와 실행
  결과는 같은 작업 ID의 리뷰 파일에 적는다.

이미 넘긴 작업은 기존 경로로 마친다. 이 규칙은 새로 쓰는 명세부터 적용하고, 진행 중인
파일을 일괄 개명하지 않는다.

## 언어

명세는 한국어, Claude의 리뷰와 구현 보고는 영어, 오래 남는 절차 문서와 Wiki 기록은
한국어다. 인용한 코드·식별자·원문 발췌는 원래 언어를 지킨다. 리뷰에서 나온 것이 지속되는
계약이나 결정 기록이 될 때는 해당 소유 문서에 한국어로 요약해 옮긴다.

## 절차

1. Codex가 작업 ID를 정하고 `tasks/_template.md`를 써서 `tasks/<작업 ID>.md`에 범위·근거·
   검증 계획·완료 기준을 적는다.
2. 사용자가 한 줄로 Claude의 검토를 시작한다 — 예: "`tasks/<작업 ID>.md` 검토해줘".
3. Claude가 명세를 현재 코드와 대조해 지적·근거·수정 제안·미해결 질문을
   `tasks/<작업 ID>.review.md`에 쓴다.
4. 사용자가 그 경로를 Codex에게 넘긴다. Codex가 리뷰를 읽고 원래 명세를 고친다. 승인된
   범위 안의 누락과 수정은 다시 확인받지 않는다. 수정 횟수에 상한을 두지 않는다. Claude가
   읽거나 구현하는 중인 명세는 그 단계가 끝난 뒤에 고치고, 새 요구는 새 ID의 후속 명세로
   만든다. 응답 전 아래 「리뷰 결과 기록과 종료 확인」의 공통 항목을 따른다.
5. 범위가 바뀌는 것, 상충해서 풀리지 않는 요구사항, 새 근거 없이 되풀이되는 이견은
   사용자에게 가져간다. 필요한 결정과 그 결과를 밝히고, 조용히 다른 범위를 고르지 않는다.
6. 구현이 승인되면 Claude가 고친 명세를 구현한다. 승인이 이미 있었다면 다시 묻지 않는다.
   범위 안의 문제는 Claude가 고치고 해당 품질 검사를 돌린다.
7. Claude가 같은 리뷰 파일에 구현·검증 보고를 덧붙인다 — 바뀐 파일, 실제로 돌린 명령과
   결과, 돌리지 않은 검사와 이유, 남은 문제, 명세와 달라진 점. 미해결 지적을 완료 주장으로
   덮지 않는다.
8. Codex가 보고를 읽고 해당 코드 변경을 완료 기준과 대조한다. Claude가 막는 지적을 고치고
   보고를 갱신해야 작업이 끝난다. Codex의 결과 리뷰가 Claude의 테스트 실행을 대신하지
   않는다. 판정과 수정 지시는 같은 ID의 명세에 기록하고,
   아래 「리뷰 결과 기록과 종료 확인」의 공통 항목과 결과 리뷰 항목을 따른다. 지적 때문에
   다시 구현이 필요하면 아래 수정 정책을 따른다.
9. 최종 리뷰와 필요한 검증이 끝난 뒤, Claude가 남길 정보를 보존하고 아래 정리 조건을
   확인한 다음 임시 작업 파일 둘을 지운다.

## 리뷰 결과 기록과 종료 확인

사용자가 Codex에게 `tasks/<작업 ID>.review.md`의 검토나 결과 리뷰를 요청하면, 같은 ID의
명세 반영까지 요청한 것으로 다룬다. 별도로 "파일을 수정해줘"라고 말할 필요가 없다.
사용자가 명시적으로 읽기 전용 검토를 요청한 경우에는 그 제한을 따른다.

**공통 항목** — 절차 4단계와 8단계에 모두 적용한다.

1. Codex는 Claude의 검토·구현 단계가 끝나 명세를 안전하게 수정할 수 있는지 확인한다. 읽은
   리뷰와 현재 변경을 대조한 뒤, `tasks/<작업 ID>.md`의 해당 요구사항과 상태를 갱신한다.
   Codex의 판정은 명세에 남기고, Claude 소유의 `.review.md`는 대신 수정하지 않는다.
2. Codex는 저장한 명세를 다시 읽어 판정·미해결 지적·수정 지시와 상태가 일치하는지 확인한다.
   추적되는 파일은 diff로 함께 본다 — 새로 만들어 아직 추적되지 않는 명세는 diff가 비어
   있다. 응답에만 적은 의견으로 인수인계를 마치지 않는다. 같은 리뷰와 변경을 다시 확인했을
   때 기존 기록이 유효하면 중복 추가하지 않고 그 기록과 현재 상태를 확인한다.
3. Codex는 사용자에게 판정과 갱신한 명세 경로를 보고한다. 쓰기 실패나 동시 편집 때문에
   기록하지 못했다면 원인과 미반영 내용을 밝히고 인수인계가 끝났다고 보고하지 않는다.

**결과 리뷰 항목** — 절차 8단계에만 적용한다. 구현과 검증 보고를 읽은 뒤에 적는 것이므로,
구현 전인 4단계에는 해당하지 않는다.

4. Codex는 검토 날짜·리비전, 판정, 검증 근거와 남은 일을 명세에 적는다. 막는 지적은 아래
   수정 정책의 식별자·위치·근거·기대 동작·검증 기준을 갖춘다. 지적이 없을 때도 검토한
   범위와 한계, 완료 기준 충족 여부를 기록하고, 구현 완료와 보존·정리 대기를 구분한다.

## 리뷰·수정·모델 상향

아래 기준은 운영 기본값이고 공급자의 보장이 아니다. 모델 버전과 가격은 이 문서에 적지
않는다.

- 보통의 구현은 Sonnet · Medium effort로 한다. 복잡한 논리는 effort를 올리고, 어려운
  원인 분석은 Opus로 한다. 사용자의 Claude Code에서 쓸 수 있는 모델과 설정을 쓴다.
- Codex는 막는 지적마다 고정된 식별자, 해당 파일과 위치, 재현 조건이나 코드 근거, 기대
  동작, 검증 기준을 적는다. 확인하지 못한 의심은 그렇게 밝힌다.
- Claude는 코드를 고치기 전에 그 지적을 현재 코드와 테스트로 확인한다. 리뷰 한 줄은 결함의
  증거가 아니다. 지적이 틀렸거나 재현되지 않으면 반대 근거를 같은 리뷰 파일에 적는다.
- 지적, 시도한 수정, 실패한 접근, 실제 검증 결과, 남은 문제를 리뷰 파일에 남긴다. 수정
  시도는 검증이나 이어진 리뷰에서 같은 결함이 남아 있을 때 실패로 센다. **첫 구현은 수정
  시도가 아니고, 서로 다른 결함은 횟수를 공유하지 않는다.**

| 조건 | 다음 행동 |
|---|---|
| 첫 구현에서 결함이 나왔다 | 확인한 뒤 Sonnet으로 고치고 해당 검사를 돌린다. |
| 같은 결함의 첫 수정이 실패했다 | 재현 조건·로그·회귀 테스트를 보강한 뒤 Sonnet으로 한 번 더 고친다. |
| 같은 결함의 수정이 두 번 실패했다 | Opus 상향을 권하고, 더 고치기 전에 원인을 분석한다. |
| 수정이 다른 동작을 반복해 깨뜨린다 | 변경 범위를 줄이고, 횟수를 기다리지 않고 Opus 분석을 권한다. |
| 원인이 요구사항 누락·상충이거나 설계 결함이다 | 설계를 Codex에게 되돌린다. 명세를 고쳐 쓰지 않고 수정 제안만 적는다. |

모델 상향은 사용자에게 하는 권고다. 다음 세션과 모델 선택은 사용자가 쥔다. 파일을 쓰는 것이
모델을 바꾸거나 세션을 시작하지 않는다. 모델 전환 승인이 이미 있으면 그대로 유효하고, 쓸 수
없으면 그 제약을 보고한 뒤 같은 패치를 되풀이하지 않고 근거를 더 모은다.

상향할 때는 지적 식별자, 재현, 실패한 시도, 검증 결과를 함께 준다. 원인 설명을 먼저 받고
최소 수정과 검증을 잇는다. 새 근거가 나오지 않으면 맹목적인 수정 반복을 멈추고 막힌 지점이나
필요한 결정을 보고한다. 완료는 여전히 완료 기준과 미해결 지적 없음으로 판정한다 — 모델
선택은 검증이 아니다.

## 완료·보존·정리

끝난 작업 지시서가 진행 중인 작업 사이에 남으면 현재 계약으로 오인된다. 아래가 **모두**
참일 때만 Claude가 명세와 리뷰를 지운다.

- 구현이 완료 기준을 만족하고, 필요한 검사가 해명되었고, Codex의 최종 리뷰에 막는 지적이
  없다.
- 현재 계약과 동작을 해당 `.claude/wiki/knowledge/` 문서에 요약했다. 남길 값이 있는 결정은
  기존 `plan-log` 절차와 `.claude/harness.json`에 설정된 경로를 따른다.
- 두 임시 파일의 최신 내용이 확인된 Git 커밋에 있거나, 필요한 정보가 적절한 영구 문서로
  보존되었다. Git 색인에 올리기만 한 것으로는 모자라다.

보존이 덜 됐으면 파일을 남기고 남은 정리 작업을 보고한다. 이 조건을 채우려고 승인 없이
커밋을 만들지 않는다. 관련 없는 작업 파일, `tasks/_template.md`, 이 절차 문서를 지우지
않는다.

Knowledge는 지금 무엇이 참인지, Plan History는 중요한 선택과 그 이유(버린 대안을 포함해)를
담는다. 끝난 명세나 리뷰를 통째로 Plan History로 옮기지 않는다. 보존 대안을 쓴 작업은 원문
전체가 Git에 남는다고 약속하지 않는다.

## 이 절차가 다루지 않는 것

훅 동작, 유료 테스트 승인, Codex 훅 배선은 각자의 작업이 소유한다. 인수인계 절차를 설치하면서
훅 동작을 바꾸거나 다시 검증하지 않는다.
