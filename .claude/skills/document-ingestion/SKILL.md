# document-ingestion

합성 픽스처는 "코드가 의도대로 도는가"를 보여주지만 **"이 규칙이 실제로 필요한가"는 못 보여준다.**
이 저장소의 실측은 전부 실파일에서 나왔다 — HWPX 선언 높이 34206 vs 실제 98326, `NARROWLY` 가
가로, PDF 제어문자 U+0001 192개, `\n` 560개가 전부 표 행 구분자.

이 스킬은 그 실측을 **재현 가능한 절차**로 만든다.

본보기는 `.claude/wiki/task_log/routing-diff-시행령개정안.md` 다. 라우팅 검출을 사람이 확인한 정답 목록과
대조해 버그 둘(쪽 번호 계산 · 레이아웃 표)을 찾아낸 기록이다. **이 문서에 수치를 옮겨 적지
않는다** — 옮긴 값은 구현이 바뀌어도 안 따라간다.

## 1단계 — 대상과 비용을 먼저 확정한다

**순서가 중요하다. 돌리기 전에 돈이 나가는지부터 본다.**

대상 파일은 `tests/fixtures/` 에 있다. gitignore 라 환경에 따라 없다.
**없으면 조용히 skip 하고 그 사실을 보고에 적는다.** 없는데 돌린 척하지 않는다.

```powershell
.\.venv\Scripts\python.exe -c "from pathlib import Path; [print(p.name, p.stat().st_size) for p in sorted(Path('tests/fixtures').glob('*'))]"
```

실행 방식은 셋이고 비용이 다르다. **기본은 A 다.**

| 방식 | 무엇을 보나 | 비용 |
|---|---|---|
| **A. `detect_regions()` 단독** | 어디에 무엇이 있는가 — 리전 종류·쪽·개수 | **없음.** 외부 API 를 안 탄다 |
| **B. `ingest()` + 키 없는 설정** | 텍스트까지. cleaner 결과 포함 | **없음.** 폴백 경로로 돈다 |
| C. `ingest()` + 실제 키 | 유료 경로(LlamaParse·Vision)의 진짜 품질 | **과금.** 사용자 승인 필수 |

라우팅·쪽 번호·표 검출을 보는 것이면 **A 로 충분하다.** 그게 `routing-diff` 가 택한 방식이다.
B 가 필요하면 `ContentRoutingConfig` 를 키 없이 만들어 넘긴다 — `tests/conftest.py` 의
`offline_config` 픽스처와 같은 형태(`table_pdf_handler="pymupdf"`, `image_handler="ocr"`,
`cache_enabled=False`).

**C 는 먼저 묻는다.** 무엇을 위해 얼마나 호출하는지 밝히고 승인을 받는다. `-m integration` 은
어느 경우에도 자동으로 돌리지 않는다.

## 2단계 — 돌리고 센다

임시 스크립트는 **스크래치패드에 두고 저장소에 남기지 않는다.**

세는 항목은 무엇을 고쳤느냐에 따라 다르지만, 최소한 이것들이다.

- `metadata.page_count`
- 리전/요소를 **종류별로** — text · table · image
- **표와 이미지가 각각 몇 쪽에 있는지 쪽 번호 목록** (`routing-diff` 가 정답과 대조한 것이 이것이다)
- `metadata.warnings` — 개수만이 아니라 내용
- cleaner 를 탔으면 `cleaned_elements` · `removed_elements` · `removed_texts`
- 유료 경로를 탔으면 `vision_calls` · `llamaparse_calls`

재현 방법을 보고에 **명령까지 그대로** 적는다. `routing-diff` 7절이 그 형식이다 — 다음 사람이
같은 수치를 다시 얻을 수 있어야 값어치가 있다.

## 3단계 — 대조한다

**혼자 보면 아무 의미가 없다.** 비교 대상이 있어야 수치가 판정이 된다.

1. **`regression/baseline.json`** — 이전 실측이 있으면 대조한다. 없으면 `regression-test`
   스킬로 기준선을 먼저 만든다
2. **사람이 확인한 정답** — 실제 문서를 열어 "표가 진짜 몇 쪽에 있는지"를 확인한 목록.
   제일 강한 근거이고, `test_hwpx_real.py` 처럼 상수로 박아둘 수 있다
3. **같은 문서의 다른 포맷** — 같은 내용의 HWPX 파일과 PDF 파일을 비교하면 로더 문제가 드러난다
   (제어문자가 PDF 에만 있다는 것이 이렇게 나왔다)

달라진 항목만 표로 낸다. 안 바뀐 것을 나열하면 바뀐 것이 묻힌다.

## 4단계 — 차이의 원인을 실제 문서에서 확인한다

**여기가 이 스킬의 핵심이다.** 수치가 바뀐 것과 좋아진 것은 다르다.

- 차이를 발견하면 **파일 안의 값으로 재현되는지** 본다. `routing-diff` 는 사용자 목록을 안 보고도
  쪽 번호 밀림이 재현된다는 것을 보여서 원인을 확정했다
- **원인을 하나로 뭉뚱그리지 않는다.** 그 기록은 겉보기 불일치를 원인 A(쪽 번호 버그)와
  원인 B(레이아웃 표 — 버그가 아니라 설계 판단)로 갈랐다. 섞었으면 둘 다 못 고쳤다
- 실측 임계값을 새로 정할 일이 생기면 **재는 기준을 먼저 의심한다.** 무엇을 분모로 삼는지가
  임계값보다 중요할 때가 많다 — HWPX 쪽 수는 문서에 따라 크게 부풀어 있어 분모로 쓰면 안 된다
- 판정이 안 서면 **"확인 필요"로 남긴다.** 억지로 결론 내지 않는다

## 5단계 — 넘긴다

이 스킬은 **재는 것까지** 한다. 그 뒤는 각자의 자리로 보낸다.

| 나온 것 | 어디로 |
|---|---|
| **잰 수치 자체** | **`verify-log` 스킬** — `.claude/wiki/verify_log/` 에 회차로 쌓인다. 형식을 여기 복제하지 않는다 |
| 코드를 고쳐야 하는 버그 | `ingestion-specialist` (또는 사용자에게 보고) |
| 계약·규칙 위반으로 보이는 것 | `code-reviewer` |
| 무엇을 왜 골랐나 · 되돌린 시도 | `task-log` 스킬 — 형식을 여기 복제하지 않는다 |
| 기준선 갱신 | `regression-test` 스킬 |
| 설계가 안 정해져서 막힌 것 | `plan-log` 스킬 |

`verify-log` 는 이 스킬이 못 하는 것을 하나 더 요구한다 — **입력 파일의 신원**(bytes +
sha256 앞 12자)이다. `tests/fixtures/` 는 gitignore 라 이름만 적힌 수치는 다른 사람이
검증할 수 없다.

고친 것이 있으면 **회귀 테스트로 박는다.** 실파일 테스트는 파일이 있을 때만 돌고 없으면 조용히
skip 하는 규약을 따른다(`test_hwpx_real.py` · `cleaner/test_real.py`).

## 이 스킬의 범위

**재는 것만 한다. 코드를 고치지 않는다.** 고칠 것이 보이면 보고하고 넘긴다.

`-m integration` 은 자동으로 돌리지 않는다. 유료 경로가 필요하면 비용을 밝히고 허락을 구한다.

바이너리를 저장소에 커밋하지 않는다 — `tests/fixtures/` 는 gitignore 이고 그대로 둔다.
