# 전체 테스트 실행 시간이 크게 늘었다 — Fast 예산 90초에 대한 여유가 줄었다

- 날짜: 2026-11-24
- 대상: `main / cbedca9` 작업 트리 + `template-core-packs` 구현(미커밋). 로컬 Full의 pytest 단계
- 비교 기준: `.claude/wiki/knowledge/quality-env.md`의 「현재 확인된 상태」 —
  2026-11-22, **651 passed · 1 skipped, 15.80~20.97초(세 번)**
- 판정: 악화 — 기능 결함은 아니지만 Fast의 timeout 여유가 크게 줄었다

## 왜 미래 비교 가치가 있는가

**Fast는 추적 경로가 바뀔 때마다 전체 테스트를 돌린다.** 정밀 매핑을 하지 않았기 때문이고,
그 선택의 근거가 「전체가 20초쯤이라 감당된다」였다. 이번 측정에서 그 전제가 약해졌다.
`fast`의 stage timeout은 **90초**이고 `success_codes`가 `[0]`이라 timeout은 곧 실패다.

이번 작업이 `packs/`와 `templates/`를 추적에 넣어 Fast가 도는 빈도를 **늘렸으므로**, 이
숫자가 다음에 어디로 가는지가 Fast 매핑을 쪼갤지 말지의 판단 근거가 된다.

## 조건과 방법

```text
python .claude/harness/scripts/run_quality.py --profile full --require-venv
```

Windows 11, Python 3.12.5, `pytest 9.2.0`, 저장소의 `.venv`. 같은 세션에서 pytest 단독
실행(`-m pytest -q`)도 한 번 쟀다. **각 조건을 한 번씩만** 돌렸고, 아래 열 관측값은 같은
조건의 반복이 아니라 **서로 다른 시점·테스트 수의 실행**이다.

## 결과

| 측정 | 기준 | 현재 | 차이 |
|---|---:|---:|---:|
| 테스트 수 | 651 passed · 1 skipped | 851 passed · 5 skipped | +200 |
| Full의 pytest 단계 | 15.80~20.97초 | **38.97~65.15초** (열 번) | 기준 최대값 대비 1.9~3.1배 |
| pytest 단독(이 작업의 테스트 추가 전) | — | 66.43초 (767 passed) | — |
| **hosted CI** | Ubuntu 10.41 · Windows 26.76초 (769건) | **Ubuntu 13.76 · Windows 19.56초** (856건) | Ubuntu +32%, **Windows는 더 빨라짐** |
| Fast stage timeout | 90초 | 90초 | 유지 |
| 남은 여유 | 약 70초 | **약 25~51초** | 관측에 따라 −19~−45초 |

관측값 열 개(초): 38.97 · 39.61 · 39.75 · 40.34 · 40.60 · 42.51 · 42.66 · 59.26 · 64.28 ·
65.15. 2026-11-24~25, 같은 커밋 계열, Claude와 Codex가 각각 실행.

**이 범위 안의 새 측정은 이 문서를 고치지 않는다.** 숫자를 하나 더 적는 것이 판정을 바꾸지
않기 때문이다. 고쳐야 하는 것은 **범위를 벗어난 값**(특히 90초에 가까운 값)이나 원인을
가린 측정이다.

**배율을 하나로 적을 수 없다.** 열 관측값이 38.97~65.15초로 흩어졌고, 그중 **가장 빠른
38.97초가 당시 테스트가 가장 많은 실행(848건)**이었다. 테스트를 늘린 뒤 20초 빨라진 실행이
있으므로 **이 범위의 흩어짐은 테스트 수로 설명되지 않는다.** 무엇이 설명하는지는 재지
않았다 — 머신 상태(다른 프로세스, 디스크 캐시, 전원·발열 정책)가 유력한 후보이지만
**통제 실험을 하지 않았으므로 추정이다.** 같은 세션 안에서도 39.61초와 65.15초가 나왔다.

**처음 적었던 「약 3배」는 철회한다.** 그 숫자는 단일 실행 쌍의 비교였고, 뒤의 관측값들이
지지하지 않는다. 남는 것은 더 약한 진술이다 — 열 관측값 전부가 기준의 **최대값(20.97초)을
넘고**, 20초대가 하나도 없다. 가장 빠른 38.97초가 기준 최대값의 약 1.9배, 가장 느린
65.15초가 약 3.1배다. 즉 **방향은 관측값들이 일관되게 가리키지만 크기는 못 쓴다.**

이번 작업이 추가한 테스트는 87건이고(계약 70 + 거부 17), 그 단독 실행은 각각 5.07초와
3.13초다. 즉 **느려진 것의 대부분은 이번 추가분이 아니다** — 테스트를 하나도 더하기 전인
767건 상태에서 이미 66.43초였다.

## 판정과 근거

**악화.** 세 가지가 함께 움직였다.

1. 테스트 수가 651 → 851로 **31% 늘었는데** 시간은 기준 최대값(20.97초) 대비 1.9~3.1배다.
   선형이 아니다.
2. 「건당 비용이 올라갔다」는 설명은 **CI 측정이 약화시켰다.** 같은 커밋(`9632b25`)의 같은
   856건을 hosted CI는 Ubuntu 13.76초 · Windows 19.56초에 끝낸다. `subprocess`로 실제 CLI를
   돌리는 그 테스트들이 거기서는 싸다. 즉 **느린 것은 테스트 묶음이 아니라 이 로컬 환경**
   쪽으로 기운다. 어느 요소가 그렇게 만드는지는 여전히 재지 않았다.
3. 열 관측값이 38.97~65.15초로 넓게 흩어졌다. 배율은 못 믿지만 방향은 믿을 수 있다 —
   기준은 세 번 돌려 **15.80~20.97초**였고, 지금은 열 번 중 20초대가 하나도 없다.
   **테스트를 늘린 실행이 더 빠른 경우가 있으므로** 흩어짐은 테스트 수로 설명되지 않는다.
   그 이상은 추정이다(위 설명 참조).

기능 결함은 아니다. 851건 전부 통과하고 Full은 PASS다. 문제는 **예산**이다.

## 한계와 재지 못한 것

- **원인을 특정하지 못했다.** `--durations`로 상위 테스트를 뽑거나 커밋별로 이분하지
  않았다. 위 2번은 추정이고 측정이 아니다.
- 각 조건을 **한 번씩만** 돌렸다. 기준값은 세 번 돌린 것이라 재현 횟수가 다르다.
- **처음 적은 「약 3배」를 뒤의 관측이 뒤집었다.** 한 쌍의 비교로 배율을 적은 것이 잘못이고,
  이 문서의 판정을 숫자 하나로 요약하지 않는다.
- hosted CI는 이제 쟀다(`9632b25`, run 45426067451). **로컬의 2~3배 증가가 CI에는 없다** —
  Ubuntu는 10.41→13.76초, Windows는 26.76→19.56초다. 그래서 「묶음이 비싸졌다」가 아니라
  「이 로컬이 느리다」로 기운다. 다만 CI 런너와 이 머신은 하드웨어·디스크·보안 소프트웨어가
  모두 달라 **한 변인을 가린 비교는 아니다.**
- 머신 상태(다른 프로세스, 디스크 캐시, 전원·발열 정책)를 **통제하지 않았다.** 흩어짐이
  테스트 수로 설명되지 않는다는 것까지가 측정이고, 머신 상태가 그 설명이라는 것은
  **후보일 뿐 확정이 아니다.**

## 다시 재는 방법

```text
python .claude/harness/scripts/run_quality.py --profile full --require-venv
python -m pytest -q --durations=20
```

세 번 돌려 중간값을 쓴다. 59초가 아니라 **90초에 얼마나 가까운지**가 판단 기준이다. 원인을
가를 때는 `--durations=20`으로 `subprocess`를 쓰는 테스트가 상위를 차지하는지 먼저 본다.

90초를 넘기기 시작하면 선택지는 둘이다 — Fast의 timeout을 올리거나, 「하네스 한 파일 수정에
전체 테스트」를 쪼개 매핑을 정밀화하는 것. 후자는 2026-11-22에 「훅·공유 모듈·스키마가 서로
영향을 주어 부분 실행의 근거가 약하다」는 이유로 기각했으므로, 되돌리려면 그 근거부터 다시
본다.

## Knowledge 반영

`quality-env.md`의 「현재 확인된 상태」 표에 이번 수치를 더하고, 「시간 예산」 절이 Fast의
여유를 과장하지 않게 둔다. 원인 추정과 기각 이력은 이 문서에만 둔다.
